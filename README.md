# TIP ESG Reporting Platform

*A dissertation build on synthetic data*

---

## 1. Introduction

Tire manufacturers in the **Tire Industry Project (TIP)** report ESG data every
year — CO₂ emissions, energy, water, waste, renewables, workforce data, and
Tire and Road Wear Particles (TRWP). Traditionally this is collected the way
most industries still do it: a spreadsheet template emailed out, filled in
inconsistently, emailed back, and consolidated by hand. That process breaks
down in a few predictable ways:

- **No audit trail** — a changed number can't be traced to who changed it or why
- **No structured verification** — flagging a suspicious figure means an email
  thread, not an accept/reject/comment workflow
- **No benchmarking** — comparing companies means manually pulling numbers out
  of separate files
- **No single source of truth** — ten companies means ten files to reconcile
  every cycle
- **Inconsistent units** — the same KPI reported in tonnes, kWh, GJ, or litres
  depending on who filled in the template that year

**This platform replaces that cycle with one web application**: companies
submit KPIs into a shared, structured template and flag anything with a
comment; analysts review, verify, and benchmark across companies from one
live dataset instead of a folder of spreadsheets.

## 2. The Data & Companies

The platform ships with **10 demo companies** configured in `config.py`:
Bridgestone, Goodyear, Michelin, Apex Tire Co, Meridian Rubber Group,
NorthStar Tyres, Summit Polymer Industries, TerraGrip Industries, Velocity
Rubber Corp, and Pinnacle Elastomers.

> ⚠️ The first three are real, publicly known tire manufacturers used here
> purely as recognisable placeholder names — **no data attached to them in
> this repository is real.** Every figure for every company, including
> those three, is synthetic data generated by `generate_dummy_companies.py`.
> This matters for two reasons: this is a public dissertation submission, and
> the real platform holds genuinely confidential client data that must never
> appear in a public repo. If you'd rather the demo used entirely fictional
> names end-to-end, that's a one-line change in `config.py` — just ask.

### 3.2 This build vs. the real, deployed platform

| | **Production (live, not in this repo)** | **This dissertation build** |
|---|---|---|
| Hosting | Microsoft Azure App Service | Runs locally on your machine |
| Database | Azure SQL Database | Local CSV files |
| File/blob storage | Azure Blob Storage | Local filesystem |
| Authentication | Azure Active Directory (real SSO) | Manual demo login form |
| Client data | Real client submissions | 100% synthetic/dummy data |
| Infra-as-code | Bicep templates, CI/CD pipeline | Not included |

### 3.3 What's deliberately not in this repo

The Azure SQL client, Azure Blob client, Bicep infrastructure templates, the
CI/CD pipeline, the SQL schema files, and the App Service startup script were
all removed for this build. None of it is needed to demonstrate the
application logic, and it either only makes sense against a real Azure
subscription or risks exposing internal infrastructure that doesn't belong in
a public academic repository. The app runs unchanged without it — it simply
falls back to local CSV storage and a local login form.

## 4. Results

Two things this dissertation measures: how the sector's sustainability
metrics have moved over time, and how much manual effort the platform removes
compared with the spreadsheet process it replaces.

**Sector trends.** Across the sector, energy intensity has stayed roughly flat
while renewable-energy share has climbed steadily since 2009 — decoupling
energy use from carbon impact rather than reducing energy use itself. CO₂
intensity in 2025 clusters most companies in the 0.60–0.89 tCO₂/t range, with
a longer tail of laggards above 0.90.

<img src="images/result_sector_intensity_renewable_share.png" width="600">
<img src="images/result_co2_intensity_distribution.png" width="500">

**Reporting effort, manual vs. platform.** Measured across three companies,
every stage of the reporting cycle — collection, processing, validation,
analysis, verification — takes markedly fewer analyst-hours on the platform
than the manual process, with the biggest gains in validation and analysis.
Total cycle time per company drops from roughly 18–21 hours to 7–8 hours.

<img src="images/result_reporting_cycle_time.png" width="480">

**Why unit standardisation matters.** Before the platform, KPI fields were
reported in as many as 7–8 different units across companies (energy fields
especially). Estimated manual reporting time across seven companies without
standardisation ranged from 24 to 32 analyst-hours — most of that variation
traceable to unit reconciliation, not the underlying data collection itself.

## 5. Running It Yourself

```bash
# 1. Create and activate a virtual environment
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. Launch — the demo dataset is already included, no setup script needed
streamlit run app.py
```

Open the URL Streamlit prints (usually `http://localhost:8501`) and sign in:

- **TIP Client Company** → any of the 10 company emails above (e.g.
  `bridgestone@tip-reporting.com`), prefilled by default
- **dss+ Analyst** → any `@consultdss.com` email, prefilled by default

The password field defaults to `demo1234` — a hardcoded local-demo
convenience, not a real credential.

## 7. Notes

- **One master CSV, not one file per company** — a single wide-format file is
  the one source of truth; per-company views are derived, not stored separately.
- **`data_loader.py` is deliberately Streamlit-free**, so the read layer could
  be pointed at a different backend without rewriting it.
- **Every comment event is versioned** — save, seen, reject, and accept each
  produce their own audit-trail entry.
- **No kaleido dependency** — PDF charts use matplotlib's Agg backend instead
  of Plotly's image export.
- This repository demonstrates the *application design* — the submission →
  verification → benchmarking workflow and the data architecture — independent
  of any specific cloud vendor and without touching real client data. The
  Azure-specific version runs in production, but it isn't the point being
  demonstrated here.
